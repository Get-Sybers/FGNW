# Changelog

All notable changes to the Get-Sybers FGNW Ludus source — the FGNW blueprint
and campaign, the `get_sybers.range` and `get_sybers.templates` collections,
the task-roles under `ansible/roles/` and the Packer template library — are
documented here. The format is [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)
and this project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html)
(`0.y.z` until the interface is stable). Each collection's version lives in its
`galaxy.yml` and its own `CHANGELOG.md` is generated by `antsibull-changelog`
from `changelogs/` (fragments go there, never into that file by hand); the
blueprint's deploy-pipeline version lives in `blueprints/FGNW/blueprint.yml`.

This repository merges two sources that were versioned separately: the range
tier (the blueprint, `get_sybers.range`, the `get_sybers.range_*` task-roles)
and the cross-tier library (the shared task-roles, `get_sybers.templates`, the
template library). Their `0.1.0` sections below predate this repository, which
has no release tag yet.

## [Unreleased]

### Fixed — Packer plugin install survives GitHub asset-CDN 504s

- **`scripts/install_ludus_packer.sh` fetches plugin binaries and checksums through the GitHub
  release API when the asset CDN fails.** GitHub's `releases/download/...` asset CDN began returning
  HTTP 504 for the Packer plugin assets (both the binaries and their `SHA256SUMS`) around 2026-11-09
  06:00 UTC, failing the `packer-smoke` job (and its `ludus-source-green` rollup) on the merge of
  #41 (`0efa249`) — even though nothing in the repo changed: the job's inputs were byte-identical to
  the 15+ runs that passed over the preceding three days, and the identical branch code passed eight
  minutes earlier. When `packer plugins install` fails, the fallback now pulls the binary from the
  `api.github.com` per-asset endpoint (which stays reachable when the CDN 504s) and verifies it
  against the release's per-asset `digest`, falling back to the `SHA256SUMS` asset (also via the API)
  for releases without a digest. The checksum gate is unchanged. Unauthenticated on public repos; an
  optional `PACKER_GITHUB_API_TOKEN`/`GITHUB_TOKEN` is used only to lift the anonymous rate limit and
  is never stored.

### Fixed — the Sand (Sunagakure) macOS mail server now actually stands up

- **`fgnw_mac_mail_server` could never work on the Sand macs, and is rewritten.** The old role
  `brew install`-ed Dovecot (the Sand macs have no Homebrew), created OS mailbox accounts, and
  wrote `/etc/postfix/main.cf` — all impossible on a SIP-enabled, Homebrew-less macOS guest. The
  rewritten role builds Dovecot from source with the Command Line Tools clang (one macOS
  portability flag, plaintext `--with-ssl=no`); serves virtual mailboxes from a `passwd-file` of
  the Sand AD users with their own AD passwords (so IMAP/SMTP auth matches the domain account); and
  runs the stock Postfix binary from a writable alternate config directory under `/usr/local`,
  because Apple's `/etc/postfix` is SIP-locked. Both services run as LaunchDaemons. Validated end
  to end on the live range (SMTP to LMTP to Dovecot Maildir to IMAP).
- **Service start/restart go through the official `community.general.launchd` module.** Loading both
  daemons (`state: started`), the restart-on-config-change handlers (`state: restarted`), and
  retiring the stock Apple Postfix daemon (`state: unloaded`) now use the module instead of
  hand-rolled `launchctl` shell. Only the from-source Dovecot build (no module compiles from source)
  and the persistent `launchctl disable` of the SIP-protected Apple daemon remain shell/command.
  Verified on the live range: both daemons cycle cleanly and re-runs report no change.
- **New `ansible/nexus-cache-dovecot.yml` (Phase 0) caches the Dovecot source on the Nexus**, the
  same pattern as the Thunderbird and GHOSTS caches, so the mail host builds inside containment with
  no egress. Wired into `phase0-nexus.yml`; `dovecot` is dropped from the Phase 1c Homebrew package
  list and the artifact is documented in `ludus-requirements.yml`.

### Added — GHOSTS macOS persona activity is deployed automatically

- **New `ansible/FGNW-mac-ghosts-activity.yml` seeds the macOS persona's browsing timeline.** The
  Windows GHOSTS personas get their per-persona `timeline.json` from `FGNW-ghosts-activity.yml`, but
  the macOS persona (Gaara, on `suna-ws1`) had none — the GHOSTS Universal client installed by
  `fgnw_mac_ghosts_client` sat idle on a fresh deploy. The new play renders a browser-only timeline
  from the same `content/ghosts/persona-timelines.yml` + `persona-overrides.yml` data, writes it to
  `<install_dir>/config/timeline.json`, and restarts the LaunchAgent so it loads. It drives a
  **visible** Chrome for Testing through the `BrowserChrome` handler's `executable-location` arg
  (never curl), honours the persona's `pace` and `active_hours` (a full-day persona becomes
  always-on, via zeroed `UtcTimeOn`/`UtcTimeOff`), and is wired into `phase5-emulation.yml` beside
  the Windows play; macOS hosts with no GHOSTS persona are skipped. A dedicated Mac timeline
  template, `templates/FGNW-ghosts-mac.timeline.json.j2`, omits the Windows-only `Command`
  recon/admin legs (those are `ghosts.exe`-only).

### Fixed — GHOSTS macOS client builds from source, installs from Nexus, drives a real browser

- **`fgnw_mac_ghosts_client` could never install Gaara's client.** Its default tarball URL
  (`ghosts-client-universal-osx-x64-<ver>.tar.gz` on github.com) is a 404 — GHOSTS ships no macOS
  build (only linux/win universal + lite) — and its launchd plist ran `<install_dir>/ghosts`, a
  binary that does not exist (the apphost is `Ghosts.Client.Universal`). The role now installs the
  client, Chrome for Testing and chromedriver from the range Nexus, runs `Ghosts.Client.Universal`,
  and loads it as a LaunchAgent in the GUI user's session so the `BrowserChrome` handler drives a
  **visible** Chrome (realistic browsing, the macOS parallel to the Windows personas) rather than a
  root LaunchDaemon with no GUI session.
- **New `nexus-cache-ghosts-universal.yml` (Phase 0) builds and stages the macOS client.** Since
  there is no upstream macOS artifact, it builds the osx-x64 Universal client from `cmu-sei/GHOSTS`
  source (self-contained .NET), downloads Chrome for Testing + the matching chromedriver (mac-x64),
  and uploads all three to the Nexus `tools/` path, skipping any already cached. Wired into
  `phase0-nexus.yml`; the three artifacts are documented in `ludus-requirements.yml`.

### Fixed — GHOSTS user-emulation timelines render, and personas auto-logon

- **`ansible/templates/FGNW-ghosts.timeline.json.j2` now renders valid JSON.** The template embedded its
  prose explanations as raw text inside the JSON (a bare `{` and running prose, not Jinja `{# #}`
  comments), so every rendered `timeline.json` was malformed: the GHOSTS client threw
  `JsonReaderException` and crash-looped in `Orchestrator.Run`, no timeline ever loaded, and the
  emulation produced no activity at all. Every comment block is now a real `{# … #}` Jinja comment and
  the stray `{` markers inside the event objects are gone; the rendered output is valid JSON across the
  plain, admin, recon/DoS and lunch-plus-night-shift persona shapes.
- **`content/ghosts/persona-timelines.yml`: correct the child-domain NetBIOS names.** The `konoha-*`
  personas said `KONOHA`, `oto-ws1` said `OTO` and `suna-ws1` said `SUNA`, but the real NetBIOS names are
  `KONOHAGAKURE`, `OTOGAKURE` and `SUNAGAKURE`, so `FGNW-persona-autologon.yml` could not translate the
  persona account to a SID and no Leaf, Oto or Sand persona logged in (only Akatsuki, which matched).
- **`content/ghosts/persona-overrides.yml`: quote the `active_hours` times.** `05:00:00` / `00:00:00` /
  `23:59:00` were unquoted, so YAML parsed them as sexagesimal integers and the active-hours to UTC
  conversion in `FGNW-ghosts-activity.yml` crashed (`list object has no element 1`) for `konoha-ws5` and
  `suna-ws1`.
- **`FGNW-ghosts-activity.yml`: derive the timezone offset reliably.** The `fgnw_ghosts_tz_offset` default
  used `now(fmt='%z')`, which returns an empty string on a naive-datetime controller, so the active-hours
  conversion crashed before any client started; it now defaults to `lookup('ansible.builtin.pipe', 'date +%z')`.

### Fixed — Sand macOS hosts bind to the child domain (join account + resolver)

- **`FGNW-mac-ad-bind.yml` binds with the child domain's `Administrator`, not `domainadmin`.**
  `sunagakure.wind.ninja` is a child domain stood up by the `ludus_child_domain` role, and Ludus
  creates the `domainadmin` principal only in the primary domains it builds directly — the child
  has none, so `dsconfigad -add` failed with `Authentication server encountered an error (5202)`.
  The play and `vars/FGNW-mac-ad-bind.yml` now join as the child's built-in `Administrator`, a
  Domain Admin of `sunagakure.wind.ninja`, with the lab password.
- **The play points each Sand Mac's resolver at the Sand child DC before binding.** Ludus hands
  the macOS hosts the range router (`10.x.20.254`) as their resolver, which does not serve the
  Sand AD SRV records (and testing-mode AdGuard does not forward them), so `dsconfigad` on
  `suna-mail` could not reach the KDC (`Authentication server could not be contacted (5200)`). The
  play now sets the primary network service's DNS to `10.<second-octet>.20.10` (`suna-dc1`) before
  the bind — the play-side resolver fix `FGNW-ninjasploitable-join.yml` already uses for the Linux
  realm-join, and the correct end state for a domain-bound Mac. The `fgnw_mac_dsconfigad` role is
  unchanged; its docs' example principal is now `Administrator`.

### Fixed — Phase 4e installs Thunderbird inside containment, and its mail names resolve

- **`fgnw_thunderbird` installs from the range Nexus instead of the internet.** The role ran
  `chocolatey.chocolatey.win_chocolatey` with no source: the community `thunderbird` package is a
  stub whose install script downloads the installer from `download.mozilla.org` at install time,
  which Phase 2 containment blocks (Nexus's `chocolatey-proxy` mirrors the package metadata, never
  that download), and the workstations' Chocolatey knew only the community source anyway. The
  macOS branch expected a Homebrew cask from Phase 1c that no play installs. Both branches now
  fetch Mozilla's installer from `raw-hosted/tools/` on the range Nexus, pinned to Mozilla's own
  `SHA512SUMS`, install it silently when Thunderbird is absent or not
  `fgnw_thunderbird_version` (142.0), verify the installed version, then write `policies.json`.
  The Chocolatey vars are gone from the role (`defaults`, `argument_specs.yml`, `README.md`).
- **`campaign/ansible/nexus-cache-thunderbird.yml` caches both installers on Nexus in Phase 0**,
  while the controller still has internet, with the pins from the role's defaults;
  `deploy-tasks/phase0-nexus.yml` runs it after `nexus-seed-all.yml`, and
  `ludus-requirements.yml` lists the two artifacts. The play lifts `raw-hosted`'s strict
  content-type validation only for the upload (Nexus classifies the xz-compressed DMG as
  `application/x-xz` and refuses it under its `.dmg` name) and puts it back.
- **The mail servers are addressed as `mail.<domain>`, the name the `dnsforwarder` role publishes.**
  `vars/FGNW-thunderbird-map.yml` named `konoha-mail.konohagakure.fire.ninja` and
  `suna-mail.sunagakure.wind.ninja`, which exist nowhere in range DNS (the Exchange VM registers
  as `<range-id>-konoha-mail` in the forest-root zone; the Sand Mac never registers), so every
  configured client pointed at an unresolvable host. The `dnsforwarder` probe now also accepts
  TCP 22, so the Sand Postfix/Dovecot Mac, which has no WinRM, gets its
  `mail.sunagakure.wind.ninja` record the way the Exchange host gets
  `mail.konohagakure.fire.ninja`.
- **The Exchange IMAP play now really sets `LoginType: PlainTextLogin`.** `FGNW-thunderbird.yml`
  ran `Set-ImapSettings` as the local WinRM user, which holds no Exchange RBAC role:
  `Get-ImapSettings` failed with "the supplied credential … is invalid", the loop ran over
  nothing and the task reported `IMAP_LOGIN_TYPE_ALREADY_SET`, leaving the server on
  `SecureLogin` (IMAP advertised `LOGINDISABLED`, so the cleartext login the clients are
  configured for was refused). The task now runs as the forest-root Administrator with
  `runas`, the way the other Exchange plays do (`vars/FGNW-thunderbird-imap.yml` carries the
  map), stops on any error and verifies the login type after setting it.
- `blueprints/FGNW/blueprint.yml` is 0.6.0: Phase 0 gained a step and Phase 4e's contract changed
  (it needs the Nexus artifacts, not internet egress). `DEPLOY.md` and `Index.md` describe both.
- Verified on a contained range (testing mode on, no egress carve-out beyond Nexus): the cache
  play populated Nexus and skipped the artifact already there; the Windows branch installed
  142.0 on a workstation wiped beforehand and skipped the four that had it; the macOS branch
  installed from the DMG; every client's policy names `mail.<domain>`, which resolves from both
  platforms once `dnsforwarder.yml` has run; and the Exchange IMAP service stopped advertising
  `LOGINDISABLED` after the elevated task ran.

### Fixed — the appxfix images disable the Edge updater's scheduled tasks too

- **`remove-appx-sysprep-blockers.ps1` (win2022-server-x64-appxfix, win2022-exchange2019-x64,
  win10-22h2-x64-enterprise-appxfix) now disables the `MicrosoftEdgeUpdateTaskMachineCore` /
  `…UA` scheduled tasks and sets the per-app update policy, not only the two services.** The
  tasks launch `MicrosoftEdgeUpdate.exe` directly, so on a deployed clone the updater still ran
  with the services disabled, installed a newer Edge, and Edge's installer registered the
  `Microsoft.MicrosoftEdge.Stable` sparse package for the logged-on user; the first deploy-time
  Sysprep then failed on it ("installed for a user, but not provisioned for all users",
  0x80073cf2) and fell back to Ludus's remove-and-retry rescue, costing a full extra Sysprep
  cycle on the DCs that had run longest before their batch. The win10 image had no updater
  handling at all. A running updater is stopped, the tasks are stopped and disabled, and
  `UpdateDefault`, `Update{56EB18F8-…}` (the Stable channel) and `AutoUpdateCheckPeriodMinutes`
  are set to 0. Rebuild the three templates to pick it up.

### Fixed — template builds install their collections on a Ludus server

- **`ninjasploitable`, `win2022-server-x64-appxfix` and `win2022-exchange2019-x64` install their
  collections with a `shell-local` provisioner, not the `ansible` provisioner's `galaxy_file`.** The
  packer ansible plugin runs `ansible-galaxy` with packer's own environment and ignores
  `ansible_env_vars`, so on a Ludus server — whose service runs with `ProtectHome=read-only` —
  it died creating `~/.ansible/tmp` (`Read-only file system`, exit status 5) and every build with a
  `galaxy_file` failed at the first Ansible step. The install now runs with `ANSIBLE_HOME` /
  `ANSIBLE_LOCAL_TEMP` under `ansible_home` and lands in the user's collections (the first entry of
  the `ANSIBLE_COLLECTIONS_PATH` Ludus exports), where the `ansible` provisioners find it.
- **The two Windows templates pin `get_sybers.templates` as a git source at a commit** instead of a
  relative `type: dir` path, the same way `macos-sequoia-15` does: Ludus copies an installed template
  dir outside the repo tree, so `../../ansible/collections/get_sybers.templates` did not resolve and
  the install would have failed anyway.

### Fixed — macOS template builds unattended on a stock Ludus node

- **`get_sybers.templates.macos_template` picks a build storage the Ludus token can use.** The
  role installs on the local storage with the most free space when the template pool is networked,
  but Ludus grants its users `Datastore.AllocateSpace` on its own VM and ISO storages only, so on a
  stock node the roomiest local storage (a bare `local-zfs`) was one the build token could not
  allocate on and VM creation failed with a Proxmox permission error — the build was not unattended
  after all. PREPARE now checks each candidate's effective privileges (`/access/permissions`) and
  skips the unusable ones, reporting what it skipped; an explicit `build_storage_pool` the token
  cannot use fails fast naming the privilege to grant, and with no usable local storage the install
  falls back to the pool with a warning (collection changelog fragment).
- **`templates/macos-sequoia-15/requirements.yml` pins the collection to a commit.** The build
  installs `get_sybers.templates` from this repository at build time; it tracked `main`, so a build
  was not reproducible and could pick up collection changes the installed template was never tested
  with. It is now pinned to a 40-hex commit SHA (the repo's pin discipline for git sources), to be
  bumped when the collection changes.
- `templates/macos-sequoia-15/Building.md` no longer refers to the macOS templates removed in #21;
  the host prerequisites in the template and role READMEs document the storage privilege.

### Added — Ludus-source CI: convention linter, Packer smoke, reference drift

Brings the native Ludus-source CI from the LudusPlusPlus source into FGNW, as an
additive layer: FGNW's existing `ci.yml`/`conform` gate is unchanged, and the
checks LudusPlusPlus's own CI shares with it (yamllint, ansible-lint, shellcheck,
shfmt, actionlint) are already covered by prek + conform and are not duplicated.

- **`scripts/ludus_source_lint.py`** (`make lint-source`, self-tests
  `make test-source`) — holds every template, blueprint and range-config to the
  native Ludus conventions, with the rules derived from facts vendored under
  `ludus-reference/` (the build-time variables Ludus injects, the Proxmox builder
  bindings, default credentials, builtin and Bad Sector Labs template names, and
  the range-config JSON schema). Taught the macOS exception: a `null`-source
  template whose `vm_name` contains `macos` skips the Proxmox-builder rules
  (T007/T010), so FGNW's whole source lints clean.
- **`scripts/packer_smoke.sh` + `scripts/install_ludus_packer.sh`**
  (`make packer-tools` then `make packer-validate`) — `packer fmt -check` +
  `packer validate` run with the exact Packer plugin set (badsectorlabs/proxmox,
  hashicorp/ansible) and `-var` set the Ludus server uses, so a template that
  validates here validates on a Ludus server. This covers the class of defects —
  truncated builds, missing Ludus variables — that `conform` does not.
- **`.github/workflows/ludus-source.yml`** — a new required check
  (`ludus-source-green`, registered in `.github/rulesets/main.json`) running, on
  every PR and push, the linter + self-tests, the Packer smoke, and a
  `reference-check` that re-derives `ludus-reference/` from the exact upstream
  commits each file records as its `provenance` (not `main`) and fails on any
  mismatch — so a hand-edit or a stale reference file is caught on the pull
  request, while upstream Ludus advancing stays the weekly drift job's concern.
  `update_ludus_reference.py` normalises the copied range-config schema (no
  trailing whitespace, one final newline) so the committed copy is hook-clean and
  round-trips through the check.
- **`.github/workflows/ludus-reference-drift.yml`** — a weekly job that
  re-derives `ludus-reference/` from upstream Ludus `main`
  (`scripts/update_ludus_reference.py`, `make update-reference`) and opens a
  tracking issue when the facts the rules depend on have changed.
- Pins `python-hcl2`, `jsonschema` and `pytest` in `test-requirements.txt`, and
  scopes the vendored test fixtures and reference data out of the yamllint /
  ansible-lint / markdownlint / gitleaks gates.
- `ninjasploitable-x64-server.pkr.hcl`: both ansible provisioners now set
  `ANSIBLE_LOCAL_TEMP` / `ANSIBLE_PERSISTENT_CONTROL_PATH_DIR` /
  `ANSIBLE_SSH_CONTROL_PATH_DIR` under `ansible_home` (linter T017), matching the
  macOS template.
- Documented in `doc/ludus-source-ci.md`, linked from `doc/index.md`. The house
  standards under `doc/standards/` are carried verbatim from their source and
  are left unchanged.

  via `import-from`), then a stdlib-only console driver (VNC over the Proxmox API, `VM.Console`
  only - no root, no `qm`) erases the disk, runs `startosinstall --agreetolicense --nointeraction`,
  waits the installer out, boots Recovery again from the OpenCore picker and injects a first-boot
  LaunchDaemon that creates `localuser`, enables SSH and skips Setup Assistant. FINALIZE (guest
  provisioning, OpenCore embed, template conversion) runs in the same build.
- **The "sealing hang" was storage latency, not macOS.** The installer's last phase (APFS snapshot +
  seal, "Less than a minute remaining") is a stream of small synchronous writes that crawls at
  ~100-200 writes/s on Ceph RBD (~20 ms per write) and looks hung for hours; on a local zvol the
  same install completes in ~15 minutes. The role now installs on the local storage with the most
  free space whenever the template pool is a network type, and FINALIZE moves the finished disk to
  the pool (`build_storage_pool` / `macos_template_build_storage` overrides it).
- Fixes in the shared provision play found by the first end-to-end run: the OpenCore CD is mounted
  before its EFI folder is embedded (macOS does not auto-mount the hybrid ISO), and the in-guest
  shutdown no longer uses `async` on `raw` (unsupported; it failed every FINALIZE). Each
  `macos-*` `.pkr.hcl` gains `build_storage_pool` and `install_timeout`.
